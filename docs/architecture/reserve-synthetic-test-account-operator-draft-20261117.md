# Draft: Reserve synthetic-test-account operator (17 November 2026)

**STATUS: CI-only prototype; intentionally not a hosted migration or production administrator console.**
This branch is stacked on draft PR #9. No live Supabase project, staff account, tenant, booking or customer record was changed. Never merge/deploy/operate against hosted data without separate explicit authorisation.

## Why a dedicated operator path?

Reserve M1 records durable user projections, memberships, role assignments, invitations, and append-only audit events with **ON DELETE RESTRICT** references. This is deliberate integrity protection. Removing an Auth user despite those references would destroy accountability. An account being called "test" is not proof that its records are disposable.

The prototype proves one **narrow, supportable** case: a fresh, trusted synthetic account with one Reserve user projection and **zero memberships, role/invitation/audit references or other linked data** can be deleted without suppressing any constraints or triggers. Owners, staff with history, ordinary unmarked staging identities and unknown dependencies are blocked.

## Preview / authorisation / execution

The local operator script is `scripts/reserve-test-account-operator.mjs`.

1. Require the CI environment flag, an approved synthetic service identity, and target Supabase database/API addresses on **loopback-only disposable ports**. The script has no remote override. The privileged Auth key is taken from the **local CLI's** generated key, never the browser or a hosted secret.
2. Select an exact Auth UUID **and** email ending in `@example.invalid`. Verify both against `auth.users`; require a matching, trusted `raw_app_meta_data.veni_synthetic_fixture` marker generated by the CI fixture. User-controlled `raw_user_meta_data` cannot qualify a target.
3. Dry-run scans incoming application foreign keys to `auth.users` and `reserve.users`, the Reserve projection, email-only invitations and the application schema list. It reports blocked dependencies and a SHA-256 snapshot fingerprint, without mutation.
4. Execution requires the **same fingerprint**, `DELETE TEST ACCOUNT <exact UUID>`, and a meaningful reason. A changed plan is rejected.
5. Write an append-only `PREPARED` event, then remove only the unreferenced Reserve projection inside a serializable transaction. Membership, invitation and audit constraints remain enabled. Call genuine local GoTrue Admin hard-delete only after this.
6. Write `SUCCEEDED`, `FAILED` or `COMPENSATED` as a second immutable event. On failure, restore the projection if Auth still exists. A failed/uncertain state requires operator investigation and cannot report deletion success.
7. The CI-only `venicleanup_ci.receipts` table preserves operator ID, exact target UUID, SHA-256 email hash, plan digest, reason and outcomes. It stores no plaintext email, password or Auth token, and rejects UPDATE, DELETE and TRUNCATE.

The local test first proves owner/staff/history and unmarked identities cannot be removed. It deliberately rejects an incorrect approval hash, then deletes **one newly generated unassigned fixture**. It checks the Auth, profile and Reserve projection are gone, all six original accounts and the Reserve tenant/audit graph survive, and receipt history cannot be altered.

## Deliberate exclusions

- **No bulk-delete, tenant purge, owner bypass, business-record purge, audit rewrite, forged admin impersonation, public admin endpoint or hosted execution.**
- An owner or historically linked test account remains **blocked**. Future legitimate cleanup may involve a review-led retention/anonymisation workflow, ownership transfer, or disposal of the *entire explicitly disposable sandbox*, never cascade deletion of immutable history.
- The prototype's named `ci:` service actor is a machine fixture, **not** a human administrator. A future hosted tool must enforce real staff SSO, MFA/recent reauthentication, least privilege, explicit tenant scope, two-person approval for exceptional purges, immutable hosted audit, reviewed retention policy, a safe backup/restore and an incident recovery plan.
- The local receipt table is a disposable **test fixture**, not a migration. Create any future migration through the Supabase CLI and review all grants/RLS first.
- Website-only self-service deletion remains handled by draft PR #9. This operator deliberately covers only one unassigned Reserve projection.
