# Draft: self-service deletion for disposable Veni Accounts (17 November 2026)

**Status:** code and automated tests only. No Supabase project, hosted Edge Function, migration, real user, or production website has been modified. **Do not merge or deploy without a separate approval.**

## What is now drafted

- Account Settings requires both `DELETE MY ACCOUNT` and the **current password**.
- The Edge Function obtains the user ID from verified Supabase Auth (`getUser`), never from request JSON.
- `VENI_SHARED_RESERVE_DELETE_PREFLIGHT=enabled` and the shared Reserve self-only RPC are **mandatory**. An absent setting, missing RPC, error, unknown response, anonymous caller or missing claims **fails closed**.
- The RPC blocks active Reserve owners until ownership is transferred; any Reserve identity projection (including revoked staff/unassigned identities) blocks automatic deletion pending privacy/retention review.
- Before the privileged hard delete, Supabase Auth verifies the current password and returns a fresh session for that same UUID. Merely refreshing an old JWT is insufficient. The preflight then runs **again**.
- Only after both clean preflights and verified password does a service-role operation call `admin.auth.admin.deleteUser(verifiedUserId, false)`. Existing `ON DELETE RESTRICT` FKs are a further backstop if Reserve data appears concurrently.
- Bad inputs (including any supplied `userId`), missing password, mismatched identity, unavailable authentication and a failed admin operation do not return success.
- Unsupported passwordless/OAuth-only accounts fail closed and need a designed step-up alternative.

## Evidence / reproducible checks

1. `node --test tests/integration/reserve-account-deletion-policy.test.mjs tests/integration/account-deletion-guard.test.mjs` verifies success, flag-off, owner/history, wrong password, forged target, unknown RPC, recheck race and deletion errors.
2. The `reserve-integrated-cutover-rehearsal` GitHub Action spins up independent loopback-only Supabase/GoTrue SOURCE and TARGET containers, loads synthetic Reserve owners, staff and a pre-existing Website user with Arcana history.
3. It confirms owners and retained-history users never reach privileged deletion.
4. It creates one new `@example.invalid` Website-only identity; deliberately fails an incorrect password; confirms an ordinary user JWT cannot call the admin deletion endpoint; then uses the **same shared guard** and local generated service-role key to hard-delete that new identity.
5. It checks deleted Auth identity/profile rows and inability to sign in, while all original six Website/Reserve Auth identities, tenants, memberships, audit events and Arcana reading remain intact. SOURCE remains unchanged.
6. Service-role credentials are **generated by the disposable local CLI**; no hosted secrets or user records are used.

## Deployment / privacy gates still closed

- This draft is stacked on earlier **unmerged** integration/audit PRs. The hosted Website `delete-account` v2 currently lacks the Reserve preflight; DO NOT assume it has these changes.
- The CI-only SQL function `tests/integration/reserve-account-deletion-preflight-prototype.sql` is **not a hosted migration**. A reviewed migration must be generated by `supabase migration new`, deployed after backup/rollback preparation, then verified under real RLS before enabling the flag.
- A non-user-editable, durable deletion event/audit receipt and a human-support privacy/retention workflow must be approved before enabling for customers; check tax/payment entitlements and data export requirements as the business model expands.
- Reserve-linked **test** accounts are intentionally blocked just like real Reserve users. An admin-only *synthetic reset* would require a separately approved, auditable, explicit-target workflow with protected-host/tenant checks, rather than making the public self-service endpoint an owner-bypass.
- Before any hosted test-account deletion: identify the exact account, distinguish disposable from real identities, validate ownership and historical references, back up safely, and obtain explicit operator approval.

**Current authorization boundary:** synthetic CI deletion only; zero hosted writes, zero merges, zero deployments.
